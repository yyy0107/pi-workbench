# 国际化指南

[English](./i18n.md) | 简体中文

在 Pi Workbench 中，国际化属于实现契约，而不是开发结束后的翻译步骤。任何用户可见产品文案的改动，
都必须在同一个 Pull Request 中支持两种基础语言：

- `en-US` 是源语言、默认语言和最终回退语言。
- `zh-CN` 是必须提供的简体中文基础语言。
- locale 标识统一使用 BCP 47。
- 支持语言列表只在
  [`packages/contracts/core/src/locale.ts`](../packages/contracts/core/src/locale.ts) 中定义一次。

## 架构

| 层级                                                                                | 职责                                                |
| ----------------------------------------------------------------------------------- | --------------------------------------------------- |
| [`packages/contracts/core/src/locale.ts`](../packages/contracts/core/src/locale.ts) | 共享 `Locale` 类型、支持语言、默认语言和校验        |
| [`i18n/config.ts`](../i18n/config.ts)                                               | UI 层重导出、locale 匹配和兼容旧流程的 Cookie 名    |
| [`i18n/messages.ts`](../i18n/messages.ts)                                           | 把组件自有词典注册为一个类型安全的 catalog          |
| [`i18n/runtime.ts`](../i18n/runtime.ts)                                             | 翻译查找、回退、消息描述符和 locale-aware formatter |
| [`i18n/provider.tsx`](../i18n/provider.tsx)                                         | 客户端 Context、语言切换和偏好持久化                |
| [`i18n/server.ts`](../i18n/server.ts)                                               | 服务端 locale 解析和服务端 runtime                  |
| 各归属模块的 `i18n/en-US.ts` 与 `i18n/zh-CN.ts`                                     | 由对应组件或子系统拥有的产品文案                    |

目前的词典归属包括 `app`、`components/assistant-ui`、`components/right-workspace`、
`extensions`、`platform/extensions` 和 `workbench`。把文案加入最近的现有归属模块；新子系统拥有较多
文案时，为它建立共置的 `i18n/` 目录，并在 `i18n/messages.ts` 注册。不要建立第二个全局 catalog 或
子系统自己的翻译 runtime。

## 哪些内容必须翻译

产品作为界面文案展示的字符串都需要翻译，包括：

- 标题、正文、标签、按钮、菜单项和对话框；
- 占位符、Tooltip、Badge、空状态、加载状态和错误信息；
- 通知和确认信息；
- `aria-label`、`aria-description`、`title` 等无障碍文案；
- 内置扩展的标题、描述、命令、设置和 Surface 标签。

不要翻译稳定 ID、路由、文件路径、命令输入、源代码、日志、用户内容、模型输出或工具原始结果。
品牌名和第三方产品名保持原样，除非该产品明确提供官方译名。

持久化时保存稳定 ID、枚举值或消息描述符，而不是已经翻译的结果；这样用户切换语言后，保存状态仍然
有效。

## 新增或修改文案

1. 找到该组件或子系统拥有的词典。
2. 在 `en-US.ts` 和 `zh-CN.ts` 中加入相同的稳定语义路径。
3. 两种语言的变量及其类型保持一致。
4. 通过共享的客户端或服务端 runtime 渲染文案。
5. 格式化或回退行为变化时，补充有意义的测试。

翻译键描述语义，不描述英文写法。优先使用 `chat.composer.send` 这样的路径，不要把展示句子本身作为
键。翻译完整句子，不要在组件中拼接多个已翻译片段。

```ts
// feature/i18n/en-US.ts
import type { MessageFormatters } from "@/i18n/types";

export const featureEnUS = {
  items: {
    count: ({ count }: { count: number }, { number, plural }: MessageFormatters) =>
      plural(count) === "one" ? `${number(count)} item` : `${number(count)} items`,
  },
} as const;
```

```ts
// feature/i18n/zh-CN.ts
import type { MessageFormatters } from "@/i18n/types";

export const featureZhCN = {
  items: {
    count: ({ count }: { count: number }, { number }: MessageFormatters) =>
      `${number(count)} 个项目`,
  },
} as const;
```

在 `i18n/messages.ts` 注册归属 catalog 后，TypeScript 会推导合法键和参数结构：

```tsx
"use client";

import { useI18n } from "@/i18n/provider";

export function ItemCount({ count }: { count: number }) {
  const { t } = useI18n();
  return <span>{t("feature.items.count", { count })}</span>;
}
```

`i18n/messages.ts` 中的 `satisfies Messages` 检查会把缺少键或插值签名不兼容变成类型错误。

## 格式化数值

使用共享 runtime 返回的 formatter；它们会自动使用当前 locale：

```ts
const { date, number, plural, relativeTime, t } = useI18n();
```

- `number(value, options)` 使用 `Intl.NumberFormat`。
- `date(value, options)` 使用 `Intl.DateTimeFormat`。
- `relativeTime(value, unit)` 使用 `Intl.RelativeTimeFormat`。
- `plural(value, options)` 使用 `Intl.PluralRules`，返回该语言的复数类别。

不要写死 locale，不要拼接分别翻译的句子片段，也不要用 `count === 1` 这类仅适用于英语的判断选择
复数形式。变量优先使用命名参数，不使用位置参数。

## 客户端、服务端与扩展元数据

客户端组件使用 `useI18n()`：

```tsx
const { t } = useI18n();
return <Button aria-label={t("feature.actions.create")}>{t("feature.actions.create")}</Button>;
```

服务端代码使用 `getServerI18n()`：

```tsx
const { t } = await getServerI18n();
```

需要随 locale 变化的静态 Extension Contribution 和其他元数据使用消息描述符：

```ts
title: defineMessage("extensions.example.title");
```

用户提供的标签、工作区资源和旧版持久化值仍适合使用原始字符串。Host 可以通过共享 `text()` helper
解析 `LocalizableText`。

## 回退与失败行为

runtime 先从请求语言中查找消息，再回退到 `en-US`，不会把 key 直接显示给用户。未知消息在开发和测试
环境中抛出错误；生产环境会记录缺失消息并返回空字符串。类型安全的 catalog 注册应在运行前发现常规的
语言缺失问题。

审查回退行为时，需要区分产品文案与外部内容：产品文案必须提供两种基础语言；外部或用户所有的内容应
保持原样，不得静默翻译。

## 新增一种语言

新增 locale 是全仓库改动，应在同一个 Pull Request 中完成：

1. 把 BCP 47 tag 加入 `packages/contracts/core/src/locale.ts` 的 `SUPPORTED_LOCALES`。
2. 为每个词典归属模块新增完整词典，并全部注册到 `i18n/messages.ts`。
3. 验证 locale 匹配、设置持久化、RPC 校验和语言选择器。这些消费者都从共享契约派生合法值，不应新增
   第二份列表。
4. 验证选择器中的语言显示名和排序。显示名来自 `Intl.DisplayNames`，不要新增写死的语言名称翻译键。
5. 检查数字、日期、相对时间、复数和无障碍行为。
6. 新增或更新 locale 契约、词典结构和功能测试。
7. 对改动所承诺的公共文档补充对应语言版本。

不能只翻译入口页或语言选择器，却让应用 catalog 保持不完整。

## 文档国际化

公共入口文档遵循以下约定：

- 无 locale 后缀的文件使用英文，例如 `README.md` 或 `docs/i18n.md`；
- 简体中文使用 `.zh-CN.md`，例如 `README.zh-CN.md`；
- 每对本地化文档在顶部附近互相链接；
- 标题、链接、命令、示例和事实陈述保持结构同步；
- 代码、路径、稳定 ID、CLI 命令和 API 名称不翻译。

核心上手、贡献、安全和国际化文档的语义变化，应在同一个 Pull Request 中同步。更深入的技术文档可以
渐进翻译；需要明确链接已有语言，且不能把过期翻译伪装成最新内容。

## Review 清单

- [ ] 每条新增或修改的产品文案都同时存在于 `en-US` 和 `zh-CN`。
- [ ] 翻译键是稳定语义路径，且两种语言的插值变量一致。
- [ ] 数字、日期、相对时间和复数使用共享 formatter。
- [ ] 无障碍文案已翻译。
- [ ] 稳定 ID 以及用户、模型、工具内容保持原样。
- [ ] 持久化状态没有保存翻译后的产品标签。
- [ ] 相关测试和两种语言文档都已更新。
