# Internationalization Guide

English | [简体中文](./i18n.zh-CN.md)

Internationalization is part of the implementation contract in Pi Workbench, not a translation pass
at the end. Every change to user-visible product copy must support both base locales in the same pull
request:

- `en-US` is the source locale, default locale, and final fallback.
- `zh-CN` is the required Simplified Chinese base locale.
- Locale identifiers use BCP 47.
- The supported-locale list is defined once in
  [`packages/contracts/core/src/locale.ts`](../packages/contracts/core/src/locale.ts).

## Architecture

| Layer                                                                                                 | Responsibility                                                          |
| ----------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| [`packages/contracts/core/src/locale.ts`](../packages/contracts/core/src/locale.ts)                   | Shared `Locale` type, supported locales, default locale, and validation |
| [`packages/workbench/shell/src/i18n/config.ts`](../packages/workbench/shell/src/i18n/config.ts)       | UI-facing locale matching and the legacy cookie name                    |
| [`packages/workbench/shell/src/i18n/bundle.ts`](../packages/workbench/shell/src/i18n/bundle.ts)       | Type-safe translation bundles and catalog validation                    |
| [`packages/workbench/shell/src/i18n/runtime.ts`](../packages/workbench/shell/src/i18n/runtime.ts)     | Translation lookup, fallback, descriptors, and locale-aware formatters  |
| [`packages/workbench/shell/src/i18n/provider.tsx`](../packages/workbench/shell/src/i18n/provider.tsx) | Client context, locale changes, and installed bundle composition        |
| [`apps/web/src/i18n/server.ts`](../apps/web/src/i18n/server.ts)                                       | Request locale resolution and Web server-side runtime                   |
| Each owner's `i18n/en-US.ts` and `i18n/zh-CN.ts`                                                      | Product copy owned by that component or subsystem                       |

Current dictionary owners include the Web bundle in `apps/web/src/app/i18n/`, generic Shell bundles
under `packages/workbench/shell/src/i18n/`, the Pi contribution bundle, and the Extension Host. The
extension SDK owns only the catalog-neutral descriptor contract; the Host owns platform copy in
`packages/extension-platform/host/src/i18n/`. Add copy to the nearest existing owner. When a new
subsystem owns substantial copy, give it a colocated `i18n/` directory, expose one translation
bundle, and install that bundle at the application composition root. Do not create a second global
catalog or a subsystem-specific translation runtime.

## What must be translated

Translate every string the product presents as interface copy, including:

- headings, body copy, labels, buttons, menu items, and dialogs;
- placeholders, tooltips, badges, empty states, loading states, and errors;
- notifications and confirmation messages;
- accessibility copy such as `aria-label`, `aria-description`, and `title`;
- built-in extension titles, descriptions, commands, settings, and surface labels.

Do not translate stable identifiers, routes, file paths, command input, source code, logs, user
content, model output, or raw tool results. Brand and third-party product names remain unchanged
unless the product explicitly provides an official localized name.

Persist stable IDs, enum values, or message descriptors—not the translated result. This keeps saved
state valid when the user changes locale.

## Adding or changing messages

1. Find the dictionary owned by the component or subsystem.
2. Add the same stable semantic path to `en-US.ts` and `zh-CN.ts`.
3. Keep variables and their types identical in both catalogs.
4. Render the message through the shared client or server runtime.
5. Test meaningful formatting or fallback behavior when it changes.

Keys describe meaning, not English wording. Prefer a path such as `chat.composer.send` over a key
containing the displayed sentence. Translate complete sentences rather than assembling translated
fragments in components.

```ts
// feature/i18n/en-US.ts
import type { MessageFormatters } from "@workbench/shell/i18n/runtime";

export const featureEnUS = {
  items: {
    count: ({ count }: { count: number }, { number, plural }: MessageFormatters) =>
      plural(count) === "one" ? `${number(count)} item` : `${number(count)} items`,
  },
} as const;
```

```ts
// feature/i18n/zh-CN.ts
import type { MessageFormatters } from "@workbench/shell/i18n/runtime";

export const featureZhCN = {
  items: {
    count: ({ count }: { count: number }, { number }: MessageFormatters) =>
      `${number(count)} 个项目`,
  },
} as const;
```

After defining and installing the owner bundle, TypeScript derives the valid key and argument shape:

```tsx
"use client";

import { useI18n } from "@workbench/shell/i18n";

export function ItemCount({ count }: { count: number }) {
  const { t } = useI18n();
  return <span>{t("feature.items.count", { count })}</span>;
}
```

The translation-bundle catalog shape check makes missing keys and incompatible interpolation
signatures type errors.

## Formatting values

Use the formatters returned by the shared runtime. They use the active locale:

```ts
const { date, number, plural, relativeTime, t } = useI18n();
```

- `number(value, options)` uses `Intl.NumberFormat`.
- `date(value, options)` uses `Intl.DateTimeFormat`.
- `relativeTime(value, unit)` uses `Intl.RelativeTimeFormat`.
- `plural(value, options)` uses `Intl.PluralRules` and returns the locale's plural category.

Do not hard-code a locale, concatenate separately translated fragments, or select plural forms with
English-only checks such as `count === 1`. Named variables are preferred over positional arguments.

## Client, server, and extension metadata

Client components use `useI18n()`:

```tsx
const { t } = useI18n();
return <Button aria-label={t("feature.actions.create")}>{t("feature.actions.create")}</Button>;
```

Server code uses `getServerI18n()`:

```tsx
const { t } = await getServerI18n();
```

Static extension contributions and other metadata that must react to locale changes use a message
descriptor:

```ts
title: defineMessage("extensions.example.title");
```

Literal strings remain appropriate for user-provided labels, workspace resources, and legacy
persisted values. `defineMessage()` is the application catalog's only public descriptor
constructor: it checks the combined namespaced key and its values together. The SDK descriptor is
opaque in source, while its runtime `{ key }` / `{ key, values }` shape stays plain JSON so validated
persisted values survive reloads. Hosts resolve `LocalizableText` through the shared `text()` helper.

## Fallback and failure behavior

The runtime resolves a message from the requested locale and then falls back to `en-US`. It never
uses the key itself as user-facing copy. An unknown message throws in development and test; in
production it logs the missing message and returns an empty string. Type-safe catalog registration
should catch normal missing-locale mistakes before runtime.

When reviewing fallback behavior, distinguish between product copy and external content. Product
copy should always have both base translations; external or user-owned content should remain
literal and must not be silently translated.

## Adding a locale

Adding a locale is a repository-wide change. In one pull request:

1. Add the BCP 47 tag to `SUPPORTED_LOCALES` in `packages/contracts/core/src/locale.ts`.
2. Add a complete dictionary for every owner and expose/install each owner's translation bundle.
3. Verify locale matching, settings persistence, RPC validation, and the locale selector. These
   consumers derive their allowed values from the shared contract and should not introduce a second
   list.
4. Verify the language's display name and sorting in the selector. Display names come from
   `Intl.DisplayNames`; do not add hard-coded language-name message keys.
5. Check number, date, relative-time, plural, and accessibility behavior.
6. Add or update locale-contract, dictionary-shape, and feature tests.
7. Add localized public documentation where the change promises it.

Do not add a locale that only translates the landing page or selector while leaving the application
catalog incomplete.

## Documentation localization

Public entry documentation follows this convention:

- the file without a locale suffix is English, for example `README.md` or `docs/i18n.md`;
- Simplified Chinese uses `.zh-CN.md`, for example `README.zh-CN.md`;
- each localized pair links to the other language near the top;
- headings, links, commands, examples, and claims stay structurally aligned;
- code, paths, stable IDs, CLI commands, and API names are not translated.

Core onboarding, contribution, security, and internationalization documentation should stay in sync
in the pull request that changes their meaning. Deeper technical documents may be translated
incrementally; clearly link available languages and avoid pretending a stale translation is current.

## Review checklist

- [ ] Every new or changed product string exists in `en-US` and `zh-CN`.
- [ ] Keys are stable semantic paths, and interpolation variables match across locales.
- [ ] Numbers, dates, relative time, and plurals use the shared formatters.
- [ ] Accessibility copy is localized.
- [ ] Stable IDs and user/model/tool content remain untranslated.
- [ ] Persisted state does not contain a translated product label.
- [ ] Relevant tests and both-language documentation were updated.
