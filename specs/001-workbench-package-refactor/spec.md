# Feature Specification: Workbench 领域能力拆包

**Feature Branch**: `codex/package-refactor`

**Created**: 2026-09-12

**Status**: Ready for implementation

**Input**: 使用一套 Spec Kit 执行全仓拆包；包根为 packages/领域/具体能力，src 为真实能力源码，lib 为内部辅助源码，能力与辅助模块保留 TS/TSX，两者最多一级目录，参考 DeepSeek Harness 目录规范。

## User Scenarios & Testing

### User Story 1 - 开发者定位与维护能力 (Priority: P1)

开发者通过领域和具体能力找到唯一实现、公开接口、词典及测试，无需沿多层 extensions/builtin 子树查找。

**Independent Test**: 列出全部包根和源码深度，检查明确的职责及能力映射。

**Acceptance Scenarios**:

1. 给定任一库包，检查其位置时，包根恰好为 packages 下两级。
2. 给定任一 src 或 lib 文件，检查其相对目录时，最多经过一级子目录。
3. 给定文件预览、Explorer、目录选择或 Artifact，开发者找到独立的同领域能力包及测试。
4. 给定任一库包，src 和 lib 均有实际代码；能力实现、公开契约、组件与装配归 src，内部辅助归 lib；src 不得全为转导出，不能用空目录或编译输出代替。

### User Story 2 - 安全修改并验证接口 (Priority: P1)

开发者修改能力时，能够识别消费者，通过公开入口协作，并运行完整的所属测试；检查自动发现越界依赖。

**Independent Test**: 对检查器加入违规样例，验证真实导入会失败、测试字符串不会误报；迁移后对照测试清单。

**Acceptance Scenarios**:

1. 跨包内部引用或循环依赖出现时，检查失败并指出来源。
2. 测试从旧位置迁入 tests/ 后仍被执行，不因目录改名漏跑。
3. 已迁移包不能重新增加超层文件或深层引用。

### User Story 3 - 用户功能保持兼容 (Priority: P1)

Web 和 Desktop 用户继续使用现有会话、输入、文件、Git、浏览器、终端及设置，Runtime 行为和数据兼容。

**Independent Test**: 已有行为测试、跨宿主构建及代表性集成冒烟。

**Acceptance Scenarios**:

1. 已保存会话、设置和工作区能恢复，扩展入口和顺序保持不变。
2. 中英文及外观设置生效，Portal 和资源加载正常。
3. Pi 重连、取消、模型配置和资源重载不新增重复实例或改变协议。

### User Story 4 - 连续执行可恢复 (Priority: P2)

执行者从同一个 Spec 的 tasks.md 找到未完成任务和验证证据，并持续实施，直至全部验收满足。

**Independent Test**: Spec Kit prerequisite 脚本能定位该 Spec；任务 ID 唯一且每项有范围、依赖、消费者和完成条件。

### Edge Cases

- 现有深层目录在过渡期间由精确基线记录；新增违规仍立即失败。
- 测试代码字符串、正则和模板不是实际导入，不能产生虚假依赖。
- 图片、样式、词典同样遵守 src/lib 深度；保留结构的技能等资源移到包根并验证产物。
- 不覆盖用户未提交修改，不因包移动改变持久化键或扩展 ID。
- 停止或验证失败时保留真实任务状态，不提前标记完成。

## Requirements

### Functional Requirements

- **FR-001**: 库包根必须固定为 packages/<领域>/<能力>，不允许嵌套工作区包。
- **FR-002**: 包内 src 与 lib 均最多一级子目录，不得将业务源码转移到其他根规避限制。
- **FR-003**: 跨包必须使用公开入口和声明的 workspace 依赖；生产依赖无环。
- **FR-004**: 源码和测试模块向上相对引用最多两层；配置/资源定位另行按用途检查。
- **FR-005**: 每个独立能力必须有可定位的实现、词典、公开接口、测试及说明。
- **FR-006**: 库包测试迁到 tests/，确保测试发现和执行清单不丢失。
- **FR-007**: 统一 i18n、外观 token 和 Portal，保留双语及最终 en-US 回退。
- **FR-008**: 保留功能、协议、持久化格式、扩展 ID/顺序和服务实例作用域。
- **FR-009**: 通过可执行检查防止结构和依赖退化；精确过渡基线最终清除。
- **FR-010**: 单一 Spec 和 tasks.md 承载任务、依赖、进度及验证证据，收敛检查以实际代码为准。

- **FR-011**: 每个库包必须同时包含 src/ 与 lib/；src 承载真实能力实现、契约、组件与装配，词典/样式随所属组件共置；lib 承载有实际消费者的内部辅助实现。不得把所有实现搬入 lib 后仅生成 src 转导出壳。目录需实际使用，lib 不作为编译产物目录；构建、测试、依赖及资源检查必须覆盖 lib，不能通过移动绕过检查。

- **FR-012**: src/lib 的能力与内部辅助源码保留 TypeScript（.ts/.tsx），不因本次拆包改为手写 JS；继续通过 strict 类型检查、lint、依赖与相关行为验证。

### Key Entities

- 能力包：领域、目录、包名、职责、公开入口、允许依赖、测试。
- 迁移任务：编号、前置任务、修改范围、消费者、验证、完成状态。
- 违规基线：当前真实违规的规则、所属包与来源，迁移后删除。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 100% 库包符合两级包根、src/lib 分工和两者一级目录约束。
- **SC-002**: 跨包内部引用、超两层相对模块引用及生产循环均为零。
- **SC-003**: 每个迁移包的测试可被发现，已有测试不因迁移遗漏。
- **SC-004**: Web、Desktop 和 Runtime 完整检查、构建和规定冒烟通过。
- **SC-005**: 所有任务均有完成证据，收敛检查无未实现需求。

- **SC-006**: 100% 库包具备实际使用的 src 与 lib；lib 源码全部纳入类型、依赖、资源和测试发现检查，公开 TypeScript 入口（既有 CommonJS 构建工具除外）从 src 导出；src 含真实实现/契约而非全转导出，包内说明列出 src/lib 职责及实际辅助消费者。
- **SC-007**: 本次能力迁移不新增手写 JS 或将 TS 改为 JS，所有新增/迁移实现由所属包及消费者 TypeScript 检查覆盖；本轮试行 JS 转换及专用配置已撤回。

## Assumptions

- 全仓规划、分阶段迁移，按独立能力划分，不设置包数量目标。
- 保留现有已符合两级结构的包目录和既有包名。
- 规范针对维护者，因此目录、模块和接口约束属于用户明确要求，不是额外产品功能。
- 项目现有构建、SDK 版本、应用身份和数据布局保持兼容。
